## Этап 0. Каркас приложения — 2026-10-06

**Критерий:** 30 фото импортируются, проект закрывается и открывается без потерь.

**Как проверяется:** `npm run test:e2e` (tests/e2e/stage0.spec.ts).
1. Тест создаёт проект и импортирует 30 синтетических фото: JPEG, PNG, WebP, TIFF; Display P3; EXIF-поворот; 16 бит; прозрачность; кадры меньше прокси.
2. Выходит из приложения сразу после импорта, не дожидаясь автосохранения.
3. Запускает приложение заново и открывает проект.
4. Ожидает те же 30 плиток в том же порядке и побайтно тот же project.json.

Кроме того, 47 модульных тестов (`npm test`).

### Что сделано
- **Каркас.** electron-vite + React + TypeScript strict, npm. Три tsconfig: `core` без DOM и Node, `node`, `web`.
- **IPC.** shared/ipc.ts описывает каналы renderer↔main (invoke и события) и сообщения main↔indexer. Preload пропускает только каналы из белого списка. Main принимает вызовы только от своего renderer.
- **Проект.**
  - Создание, открытие, закрытие.
  - Автосохранение через 500 мс после изменения. Запись атомарная, предыдущая версия лежит в `project.json.bak`.
  - При закрытии и выходе изменения дописываются. Если запись не удалась, приложение спрашивает, закрывать ли без сохранения.
  - При открытии кэш сверяется: пропавшие прокси пересобираются из оригиналов, если их хэш не изменился.
- **Импорт в utility process.**
  - Потоковый SHA-256, первые 16 hex-символов становятся id ассета.
  - sharp: автоповорот по EXIF, перевод в sRGB по ICC, прокси 2048 и 512 в `cache/proxies/<id>/`.
  - Порядок в сетке совпадает с порядком файлов. Повторное фото с тем же содержимым пропускается. Если оригинал пропал, повторный импорт восстанавливает ссылку на него.
- **Протокол** `gridtone://proxy/<id>/<512|2048>` отдаёт прокси только для ассетов открытого проекта.
- **Экран:** приветствие, панель проекта со статусом сохранения, статус импорта со списком ошибок, сетка из 3 колонок с плитками 3:4.

### Находки
- **16-битные файлы.** Без `pipelineColourspace('srgb')` sharp искажает их цвет: 200/100/30 превращается в 216/93/0, P3-файл — в 187/105/49. Проверено и закрыто регрессионным тестом.

- **heic-decode** (запасной путь из спеки) отдаёт пиксели без ICC-профиля. Снимки iPhone в Display P3 молча прочитаются как sRGB. Если HEIC пойдёт через него, профиль придётся добывать отдельно. На macOS проще `sips`.
- **Две схемы из spec.md** — архитектура и дорожная карта — выгрузились в Markdown заглушками «embedded content». Их стоит перенести текстом.

## Этап 1. Цветовой конвейер и WebGL-превью — 2026-10-07

**Критерий:**
- нейтральные параметры дают тождество;
- шейдер совпадает с эталоном `core/color/pipeline.ts` на наборе эталонных изображений: средний ΔE2000 < 0.5, максимум < 2;
- ползунок меняет плитку в реальном времени;

**Как проверяется:**
- **Тождество.** `tests/core/color/pipeline.test.ts`: решётка 17³ и 2000 случайных цветов проходят без изменений, бит в бит. То же с пустым образом.
- **Совпадение шейдера.** `npm run test:e2e` → `tests/e2e/shader-parity.spec.ts`. Скрытая страница `parity.html` рисует 6 эталонных изображений с 19 наборами параметров во float-буфер. Каждая пара сравнивается с CPU отдельно.
  - Изображения: рампы, круг тонов OKLCH, кожа, почти серые, куб RGB 17³, шум. Параметры: каждый шаг отдельно, крайние значения, всё вместе с образом, три случайных набора.
  - Результат: худший пиксель ΔE2000 = 0.0007, средний ≤ 0.0001. Расхождение — только float32 против float64.
  - Тест не пустой: с намеренно испорченным контрастом в шейдере средний ΔE вырос до 0.95–1.39, и тест упал.
- **Ползунок в реальном времени и перезапуск.** `tests/e2e/stage1.spec.ts`:
  1. Импорт 6 фото, клик по плитке.
  2. Экспозиция +1 EV с клавиатуры. Плитка светлеет меньше чем за секунду, соседняя не меняется.
  3. Температура −30. Плитка холодеет.
  4. Выход сразу, не дожидаясь автосохранения.
  5. В project.json ровно эти значения. После открытия плитка выглядит так же (±1 из 255 по каналу), ползунки показывают +1.00 и −30.

### Находки
- **Строка Y матрицы sRGB** с 7 знаками в сумме даёт 1.0000001. «Яркость серого сохраняется» поэтому сверяется с Y(1, 1, 1), а не с 1.
- **Матрицы OKLab Оттоссона** с 10 знаками взаимно обратны лишь до ~10⁻⁷. Для превью это незаметно, но тесты туда и обратно идут с допуском 10⁻⁶.
- **`toEqual` в Vitest** различает 0 и −0. Для точного тождества это важно: нейтральный шаг пропускается целиком, а не умножается на 1.
- **Отличие от GLSL в core.** В GLSL `atan(0, 0)` не определён, а `1/0` на части GPU даёт NaN. Шейдер и core одинаково обходят оба случая явными проверками.
- **Prototype pollution через патчи.** Путь `['slots', 0, 'adjust', '__proto__', …]` записал бы поле в `Object.prototype`, а проверка коррекции этого не заметила бы. Ключи прототипа запрещены, промежуточные ключи должны быть собственными, состав полей коррекции и кадра проверяется строго.
- **Ползунки в e2e.** Playwright не умеет `fill` у `<input type=range>`, поэтому ползунки двигаются клавиатурой. Это и ближе к пользователю.

### Отличия от спеки
- **Таблицы кривых и HSL** — не 1D-текстуры, а строки float-атласа (в WebGL2 нет 1D-текстур). Шейдер читает их `texelFetch` и интерполирует сам, как core. Линейная фильтрация float-текстур требует расширения, и её результат не совпал бы с CPU бит в бит. spec.md обновлён.
- **Охват на шагах 7–8.** Цвет, вышедший за охват, срезается по каналам, сжатия хромы нет. Насыщенность +100 на и без того насыщенных цветах слегка сдвигает тон.
- **Поворот кадра** (`angle`) применяется, но кадр пока не ограничивается границами фото. Это придёт с редактором кадра.
- **Страница сверки `parity.html`** попадает в сборку. Приложение её не открывает.

## Этап 2. Редактор сетки — план

Согласован 2026-10-07. Три подэтапа, у каждого свой критерий, запись в журнал и коммит; каждый начинается в новой сессии.

**Уже решено:**
- Режим 7 строится по `slot.target`: рендер и шкала готовы сейчас, сами цели появятся на этапах 4–5.
- Профиль (режим 1) делается по образцу Instagram: прототипа в репозитории нет.
- Сверх границ этапа ничего не добавляется. Удаление плиток, статус «опубликован» в интерфейсе и пустые позиции — позже.
- Новых зависимостей не планируется.
- На каждом подэтапе e2e этапов 0 и 1 и сверка шейдера по-прежнему проходят.

**Общее для подэтапов:**
- **Патчи проверяются по инвариантам, а не по белому списку путей (ADR 0010).** Перестановка в Immer — это `replace slots[i]` целыми слотами, список путей её не пропустит. После пакета main сверяет:
  - набор id слотов не изменился;
  - у каждого слота (по id) все поля, кроме `adjust`, `crop` и `lookId`, прежние;
  - `lookId` указывает на существующий образ, id образов не повторяются, `importedLut` не меняется (этап 3);
  - пределы коррекции и кадра и запрет ключей прототипа — как сейчас.
  Пакет по-прежнему атомарен.
- **Undo/redo в renderer на обратных патчах Immer (ADR 0011).**
  - Одна запись — одно действие. Ползунок, точка кривой или кадр склеиваются в одну запись, пока жест не закончен.
  - Отмена уходит в main обычным пакетом, автосохранение не меняется.
  - Импорт в историю не входит. Индексы в истории верны, потому что main добавляет слоты только в конец; это условие записывается в ADR.
  - До 200 действий, при смене проекта история очищается.
- **Меню передаёт команды в renderer** новым событием в shared/ipc.ts: «Отменить», «Повторить», «Копировать правки», «Вставить правки», режимы 1–7 в меню «Вид». В текстовом поле ⌘Z работает как обычно.
- **Горячие клавиши — по `event.code`**, иначе E и `\` не сработают в русской раскладке.
- **Инспектор становится общим `AdjustPanel`:** правит поправку фото и образ, на этапе 2в работает в редакторе фото.

### 2а. История, выделение, образы, перестановка

**Критерий:** перестановка, образы и копирование правок отменяются и возвращаются; всё переживает перезапуск.

### 2б. Инструменты цвета и режимы просмотра

**Критерий:**
- кривые, HSL и круги правятся мышью и меняют плитку в реальном времени;
- клавиши 1–7 переключают режимы;
- режимы 3 и 4 совпадают с эталоном в core;
- удержание `\` показывает фото до правок.

**Как проверяется:**
- `shader-parity.spec.ts` расширяется режимами 3 и 4. Для режима 3 пороги прежние. Для режима 4 сверяется номер уровня; расхождение допустимо только у пикселей, чьё L ближе 10⁻⁴ к границе уровня.
- `tests/e2e/stage2b.spec.ts` на синтетических фото:
  - точка общей кривой, поднятая мышью, осветляет средние тона;
  - насыщенность синих −100: синяя плитка серая, красная не меняется;
  - круг теней к синему окрашивает тени рампы, света — нет;
  - 3 — плитка серая и совпадает с core; 4 — не больше 5 уровней серого;
  - 5 — заливка совпадает с доминантой core по тому же прокси (ΔE2000 < 1);
  - 6 — сетка размыта;
  - 7 — на проекте с целями в фикстуре: плитка в цели зелёная, далёкая красная, без цели серая;
  - удержание `\` возвращает исходник.

**Шаги:**
1. **Панели:**
   - `CurveEditor` — RGB, R, G, B; клик добавляет точку, перетаскивание двигает, двойной щелчок или увод за край удаляет. Линию рисует тот же `monotoneSpline` из core. В `validate.ts`: x строго растёт, не больше 16 точек;

  - окно Electron временами не выдаёт кадры, и `scrollIntoViewIfNeeded` бесконечно ждёт стабильности плитки;
  - таймаут теста в 90 с сработал через 15 минут.

  Так зависли 3 из 30 запусков отдельных тестов: дважды этап 0, чей код не менялся, и один раз этап 2а. Остальные прошли. e2e нужно запускать при разблокированном экране.
- **Папка проекта в stage2a.** Если тест упал посреди сессии, приложение закрывается в afterAll до удаления папки проекта: при выходе оно дописывает автосохранение.

### Находки
- **Снимок экрана в e2e** даёт цвет без пересчёта под дисплей: серый плитки в режиме 3 сверяется с core по абсолютному значению, а не только «до/после».
- **Порог режима 3 нечувствителен к малой ошибке.** Серый на 2% ярче (L³ · 1.02) даёт средний ΔE 0.28–0.41 при пороге 0.5. Такую ошибку ловит сверка уровней режима 4: код серого у них общий.
- **Однотонное фото с шумом JPEG** без слияния кластеров делилось на пять почти одинаковых цветов, и большое небо проигрывало меньшему объекту. Отсюда слияние кластеров ближе 0.02.
- **Доминанта градиента неустойчива:** k-means режет рампу на почти равные полосы, и от разницы декодеров JPEG на ±1 главной может стать соседняя. В e2e у рампы проверяется только наличие заливки.
- **Скорость метрик** (Node, эта машина): около 50 мс на плитку без правок, 135 мс со всеми шагами конвейера.
- **Воркер в сборке:** Vite кладёт его отдельным IIFE-чанком, создаётся он с `type: 'module'` и из file:// работает.

### Решения
- [0013](decisions/0013-crop-constraint.md) — модель ограничения кадра:
  - размер кадра зависит от угла, центр ограничивается по описанному прямоугольнику;
  - хранится заданное, ограничивается при расчёте: поворот и масштаб обратимы сами по себе;
  - правки мышью считаются от начала жеста и видимого положения;
  - окно сетки толкает кадр.
- **Без ADR:**
  - редактор показывает фото в осях фото, а повёрнутый кадр — контуром поверх. Вариант Lightroom «кадр неподвижен, фото вращается» отложен;
  - геометрия в редакторе считается по размерам оригинала из `AssetRef`, в сетке и метриках — по прокси 512. Расхождение меньше пикселя прокси;
  - номер поста в шапке — позиция в сетке, как на плитке. Вкладка редактора помнится до перезапуска;
  - образ в редакторе только виден, правят его во вкладке «Образ» инспектора;
  - опубликованный пост открывается, но не правится — ни цвет, ни кадр;
  - в CLAUDE.md — правило: геометрия кадра только в crop.ts.

### Находки
- **Окно 3:4 в кадре ленты по вертикали не ходит.** 4:5, 3:4 и 1:1 не уже 3:4, поэтому окно сетки 3:4 всегда во всю высоту кадра и двигается только по горизонтали: в кадре 4:5 — на 6% ширины. Шаг плана «окно сетки сдвинуто вниз» выполним, только если окно толкает кадр; так и сделано (ADR 0013, п. 7). Само по вертикали окно ходит только в сетке 1:1.
- **«Пиксели фона».** За краем фото шейдер повторяет крайний пиксель (CLAMP_TO_EDGE), отдельного фона нет. Поэтому у фото в e2e белая рамка: вылет кадра превращает её в белые клинья.
- **`Object.assign` по черновику Immer** с теми же значениями патчей не даёт. Движение мыши, которое кадр не меняет, пустых записей в историю не пишет.

### 3в. Калибровочная карта

**Критерий:** карта экспортируется. Карта, на которую LUT наложен в правильной точке, получает «Совпадает». Сдвинутая до LUT, без LUT или с LUT дважды получает «Не совпадает» с причиной.

**Как проверяется:**
- **`tests/e2e/stage3c.spec.ts`:**
  1. Проект с образом «Плёнка», как в 3а. «Экспорт» → «Калибровочная карта» и `.cube` 33: в подпапке `Калибровка.png` (8 бит, с профилем sRGB) и LUT.
  2. Тест играет редактор: применяет `.cube` к карте, уменьшает её вдвое и пишет JPEG q90. «Проверить карту…» с образом «Плёнка» показывает «Совпадает», средний ΔE2000 < 1.
  3. Та же карта, осветлённая на +0.3 EV до LUT: «Не совпадает», худшие патчи в отчёте.
  4. Карта без LUT — «LUT не применён». LUT дважды — «LUT применён дважды».
  5. Обрезанная карта — «Карта обрезана или повёрнута».
- **Модульные тесты:**
  - раскладка: патчи не пересекаются, поле замера внутри патча;
  - замер: карта против себя даёт ΔE 0, шум JPEG усредняется;
  - диагноз на синтетических «редакторах».

**Шаги:**
1. **core, сначала тесты** — `lut/calibration.ts`:
   - карта RGBA 8 бит: около 150 патчей (серая шкала, круг тонов на трёх уровнях L, кожа, основные и насыщенные цвета у края охвата) и градиенты для глаза, которые в замер не входят;

   - ожидание — проход образа core по цвету патча, то есть то, что видно в Gridtone. ΔE2000: средний, 95-й перцентиль, худшие патчи;
   - диагноз — ближайшая модель: без LUT, LUT, LUT дважды.
2. ADR 0016 — карта: состав, формат, замер, диагнозы. Пороги стартовые — средний < 1, худший патч < 3; их калибрует ручной чек-лист.
3. **utility process:** запись карты в PNG. Чтение возвращённой — тем же рецептом цвета, что у прокси (ICC → sRGB, ADR 0004), с приведением к размеру карты, если пропорции совпали с точностью 1%.
4. **IPC:** раздел карты в `export:run`; `calibration:check` — main спрашивает файл и возвращает отчёт.
5. **renderer:** раздел «Калибровка» в `ExportDialog` — «Сохранить карту», «Проверить карту…» с выбором образа. В отчёте вердикт, числа, худшие патчи образцами «ожидалось / получено» и подсказка.
6. Закрытие: e2e, запись в журнал, коммит.

### Находки
- **Где 33 не проходит.** Эталонные изображения × наборы сверки шейдера: на 65 проходят все 114 пар, на 33 — все, кроме шести:
  - «всё сразу и образ» × почти серые;
  - «случайно 2» × рампы и шум;
  - «случайно 3» × круг тонов, кожа и почти серые.

  Набор «кривые» на 33 проходит, кривая с изломом — нет: 99-й перцентиль 3.94 на 33 и 0.81 на 65. На наборе самой проверки (`chooseLutSize`) из наборов сверки на 65 уходит только «случайно 2».
- **Трилинейная интерполяция** на кривых совпадает с тетраэдрической (поканальная функция), на тоне почти совпадает, а на HSL и сочности грубее: на HSL средний ΔE 0.18 против 0.08.
- **16 бит в sharp.**
  - Глубину сырого входа sharp берёт из типа массива: `Buffer` читается как 8 бит, нужен `Uint16Array`.
  - Без `toColourspace('rgb16')` PNG молча пишется 8-битным.
  - При чтении 16-битного PNG без `toColourspace('rgb16')` даже `raw({ depth: 'ushort' })` возвращает 8-битные значения.
- **Скорость** (эта машина): запекание 33³ — 40 мс, 65³ — 200 мс; проверка по кругу 33 — около 0.1 с.
- **Подложка диалога** затемняет сетку на снимке экрана, поэтому e2e снимает плитки до открытия диалога.
- **e2e в этой сессии не зависали.**

  - у `sampler3D` в GLSL ES 3.00 нет точности по умолчанию — нужна `precision highp sampler3D`;

  - фильтр по умолчанию с мип-уровнями делает RGB32F-текстуру неполной, и `texelFetch` вернул бы нули: нужен `NEAREST`.
- **Float64Array через IPC** приходит в renderer и в utility process как есть: экспорт образа с LUT в 3а-задаче работает без перекладки.

### Находки
- **Чувствительность карты** («Плёнка», `.cube` 33):

- **«Дважды» и сдвиг похожи по среднему.** +0.3 EV до LUT даёт против модели LUT 3.63, против «дважды» — 3.88. Отличает их только порог «модель объясняет замер» (средний < 2): у настоящего «дважды» — 0.2.
- **sharp `withIccProfile('srgb')`** на сыром sRGB пишет точки без изменений: PNG карты совпадает с core бит в бит.
- **Тип `sharp.Sharp`** через импорт по умолчанию TypeScript 7 не находит: нужен `import { type Sharp } from 'sharp'`.
- **Синтетический шум у чёрного и белого** срезается с одной стороны и смещает среднее до 0.8 ΔE. У настоящего JPEG однотонный патч внутри почти точен, края поле замера не берёт.
- **e2e в этой сессии не зависали.**

  - всё отложенное с этапов 0–3б (списки — в записях 2в, 3а и 3б);
  - карта, повёрнутая на 180° или отражённая, проходит проверку пропорций и получает «цвет сдвинут», а не «повёрнута»;
  - «Проверить карту…» — только в диалоге экспорта, пункта меню нет; отчёт пропадает при закрытии диалога;
  - выбор образа и подсказки отчёта по каждой причине проверены e2e, а признак слабого образа — только модульно.
