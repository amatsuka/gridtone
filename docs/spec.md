# Gridtone — проект приложения для стилизации Instagram-сетки

Oct 6, 2026 · @Alex

## Суть и сценарии

Gridtone — десктоп-приложение, в котором Instagram-сетка проектируется как одно изображение. Раскладка, кадр, цвет и яркость каждой плитки подчинены общему стилю, а готовый образ уходит в ваш редактор в виде LUT. Источник правды — параметры правок: оригиналы фото никогда не меняются.

Модули спроектированы под три сценария:

- **Довести текущую ленту.** Вы загружаете скриншоты уже опубликованных постов и фото, которые готовите к публикации. Анализ показывает, какие плитки выбиваются по яркости, температуре или насыщенности, и предлагает конкретную поправку. Найденный образ экспортируется в LUT.
- **Сетка по паттерну.** Вы загружаете картинку-шаблон (например, шахматку из светлых и тёмных квадратов) или собираете её во встроенном генераторе. Приложение превращает шаблон в цели для каждой позиции, подгоняет текущие фото и строит план публикаций.
- **Как у них.** Вы загружаете скриншот чужой сетки. Приложение снимает с неё цели по позициям и общий образ, подбирает фото из вашей библиотеки и даёт перебирать кандидатов прямо в позиции.

**Границы первой версии.** В неё входят JPEG, PNG, WebP, TIFF и HEIC, сетка из трёх колонок с превью 3:4 и 1:1, глобальная цветокоррекция, экспорт LUT, постов и плана. Не входят декодирование RAW (только встроенное превью, позже), локальные правки (маски, кисти, ретушь), публикация в Instagram и работа с его API, облачная синхронизация.

**Главное архитектурное решение.** Все цветовые операции глобальные и поточечные: каждый цвет RGB меняется независимо от соседних пикселей. Только при этом условии то, что видно в Gridtone, без потерь сворачивается в LUT. Пространственные операции (кадр, поворот, виньетка, резкость) живут отдельно и в LUT не попадают.

## Архитектура и стек

Приложение на Electron из трёх слоёв: интерфейс и GPU-превью в renderer, файлы и база в main, тяжёлая обработка библиотеки в отдельном utility process. Вся предметная логика (цвет, метрики, гармония, подбор, LUT) живёт в пакете `core` на чистом TypeScript без DOM и Node. Поэтому она тестируется изолированно и одинаково работает в любом процессе.

**Цвет.** Рабочее пространство — sRGB. При импорте sharp переводит фото в sRGB по встроенному ICC-профилю (iPhone снимает в Display P3). Экспозиция и баланс белого считаются в линейном sRGB, кривые — в гамма-кодированном, как в Photoshop и Lightroom. Метрики и HSL считаются в OKLab/OKLCH: там равные числовые шаги воспринимаются как равные.

**Производительность.** Целевая слабая машина — MacBook Air M1 с 8 ГБ. Поэтому в памяти держатся только прокси (2048 px по длинной стороне для редактора, 512 px по короткой для плиток), текстуры живут в LRU-кэше, а индексатор работает пачками с ограниченным параллелизмом.

## Модель данных

Каждая правка хранится как данные в `project.json`: превью, анализ и экспорт каждый раз вычисляются из него. Проект — это папка с `project.json`, `cache/` (прокси, миниатюры) и `luts/` (копии импортированных `.cube`). Оригиналы фото адресуются абсолютным путём и хэшем, поэтому переезд папки с фото не ломает проект.

```ts
type Ratio = '3:4' | '1:1';
type Vec3 = [number, number, number];   // OKLab: L 0..1, a, b
type Pt = [number, number];              // точка кривой, 0..1

interface Project {
  version: 1;
  name: string;
  grid: { ratio: Ratio; columns: 3; pinned: 0 | 1 | 2 | 3 }; // pinned — закреплённые посты сверху
  assets: Record<string, AssetRef>; // оригиналы фото проекта, ключ — AssetRef.id
  slots: Slot[];                 // порядок = порядок в сетке, 0 — верхний левый
  looks: Look[];                 // общие образы, каждый экспортируется в LUT
  luts: Record<string, LutRef>;  // импортированные LUT, ключ — LutRef.id; меняет только main
  pattern?: Pattern;             // активная цель
  reference?: ReferenceGrid;     // разобранная чужая сетка
}

interface AssetRef {            // оригинал; сам файл никогда не меняется
  id: string;                    // первые 16 hex-символов hash
  path: string;                  // абсолютный путь
  hash: string;                  // SHA-256 содержимого
  w: number; h: number;          // с учётом EXIF-ориентации
  format: 'jpeg' | 'png' | 'webp' | 'tiff';
  icc: 'embedded' | 'assumed-srgb';
  importedAt: string;            // ISO 8601
}

interface LutRef {               // копия файла — luts/<id>.cube в папке проекта
  id: string;                    // первые 16 hex-символов hash
  name: string;                  // имя исходного файла
  size: number;                  // LUT_3D_SIZE, 2…65
  hash: string;                  // SHA-256 файла
  importedAt: string;            // ISO 8601
}

interface Slot {
  id: string;
  state: 'published' | 'planned' | 'empty'; // published — скриншот вышедшего поста, только для анализа
  assetId?: string;
  postType: 'photo' | 'carousel' | 'reels';
  crop: Crop;
  adjust: Adjust;                // поправка этого фото: приводит его к образу
  lookId?: string;
  target?: SlotTarget;           // цель из паттерна или референса
  candidates: Candidate[];       // варианты для перебора в позиции
  choiceLocked: boolean;         // выбор зафиксирован, автоподбор его не трогает
}

interface Crop {
  feed: { aspect: '4:5' | '3:4' | '1:1'; cx: number; cy: number; zoom: number; angle: number };
  grid: { cx: number; cy: number }; // окно 3:4 внутри кадра ленты, по умолчанию центр
}

interface Adjust {
  exposure: number;              // EV, −3..+3
  temp: number; tint: number;    // −100..+100
  contrast: number; highlights: number; shadows: number; whites: number; blacks: number;
  vibrance: number; saturation: number;
  hsl: Record<HueBand, { hue: number; sat: number; lum: number }>;
  grading: { shadows: Wheel; midtones: Wheel; highlights: Wheel; balance: number };
  curves: { master: Pt[]; r: Pt[]; g: Pt[]; b: Pt[] };
}
type HueBand = 'red' | 'orange' | 'yellow' | 'green' | 'aqua' | 'blue' | 'purple' | 'magenta';
interface Wheel { hue: number; amount: number }

interface Look { id: string; name: string; adjust: Adjust; importedLut?: string } // importedLut — id из Project.luts

interface SlotTarget {
  L: number;                     // OKLab L
  hue?: number; chroma?: number; // задаются, если цвет важен
  palette?: Vec3[];
  tolerance: { L: number; hue: number; chroma: number };
  hard: boolean;                 // true — плоская заливка шаблона, false — снято с фото
}

interface Pattern {
  source: 'generator' | 'string' | 'image' | 'reference';
  periodRows: number;            // паттерн повторяется вниз с этим периодом
  postingMode: 'single' | 'batch'; // переживает одиночные посты или только пачки по 3
  cells: SlotTarget[];
}

interface ReferenceGrid { imagePath: string; cells: Features[]; look?: Look }

interface AssetFeatures {        // строка индекса библиотеки в SQLite
  assetId: string; path: string; hash: string;
  w: number; h: number; takenAt?: string;
  full: Features;                // по всему кадру
  grid34: Features;              // по центральному окну 3:4
  dhash: string;                 // поиск почти-дублей
}

interface Features {
  meanL: number; p05L: number; p50L: number; p95L: number;
  lHist: number[];               // 8 корзин
  meanA: number; meanB: number; meanC: number;
  hueHist: number[];             // 12 корзин по 30°, вес = хрома
  palette: { lab: Vec3; share: number }[]; // k-means, k = 5
  neutralShare: number;          // доля пикселей с хромой < 0.03
  busyness: number;              // энергия краёв по Собелю
}

interface Candidate { assetId: string; score: number; parts: { L: number; hue: number; chroma: number; palette: number; penalty: number } }
```

## Модуль 1. Редактор сетки

Основа — уже сделанный прототип: сетка из трёх колонок, перетаскивание, кадр, типы постов. В приложении к нему добавляются два кадра на пост, два уровня цветокоррекции и режимы просмотра, в которых сетка оценивается целиком.

**Два кадра.** В ленте пост показывается в своих пропорциях (4:5, 3:4 или 1:1), а в сетке — окном 3:4 внутри него. Поэтому у поста два кадра: кадр ленты и окно сетки, которое двигается внутри первого. При загрузке в 3:4 они совпадают, и приложение предлагает этот вариант по умолчанию.

**Статусы позиций.** Опубликованные посты (скриншоты текущей ленты) заблокированы: их нельзя перекрасить, но они участвуют в анализе и задают контекст. Запланированные позиции полностью редактируются. Пустые позиции — места под план или подбор.

**Режимы просмотра** переключаются клавишами 1–7:

| Клавиша | Режим | Что показывает | Зачем |
| --- | --- | --- | --- |
| 1 | Профиль | Эмуляция телефона, как в прототипе | Итоговое впечатление |
| 2 | Рабочая сетка | Крупные плитки, номера, статусы | Работа с раскладкой |
| 3 | Яркость | Плитки в ч/б по OKLab L | Ритм светлого и тёмного без отвлечения на цвет |
| 4 | Постеризация | 5 уровней яркости | Видно, совпадает ли сетка с паттерном |
| 5 | Доминанты | Плитка залита своим главным цветом | Цветовой ритм и пятна |
| 6 | Прищур | Сильно размытая сетка | Общий баланс масс, как при взгляде на макет издалека |
| 7 | Отклонение | Тепловая карта расстояния до цели | Что править в первую очередь |

**Коррекция в два уровня**, оба поточечные:

- **Поправка фото** приводит конкретный кадр к общему виду: экспозиция, баланс белого, точечно насыщенность.
- **Образ (Look)** — общая обработка для группы постов или всей сетки. Образов может быть несколько, например два чередующихся для шахматки.

Инструменты те же, что в фоторедакторе: ползунки (экспозиция, контраст, света, тени, белые, чёрные, температура, оттенок, сочность, насыщенность), HSL по 8 диапазонам, цветокоррекция по трём кругам (тени, средние, света), кривые общая и по каналам R, G, B. Кривые интерполируются монотонным кубическим сплайном Фрича — Карлсона: в отличие от обычного сплайна, он не даёт выбросов между точками. Правки копируются и синхронизируются по выделенным плиткам; до/после показывается по удержанию клавиши; undo/redo работает для всего.

Одно отличие от Lightroom стоит знать заранее. В Lightroom «Света» и «Тени» — локальное тональное сжатие с учётом соседних пикселей, а здесь это глобальные кривые, иначе образ нельзя свернуть в LUT. На сильных значениях результат будет грубее, чем в Lightroom.

**Конвейер.** Порядок фиксирован и одинаков в шейдере, в эталонной реализации на TS и при запекании LUT:

1. sRGB → линейный.
2. Баланс белого: коэффициенты каналов из сдвига температуры и оттенка (позже — адаптация Брэдфорда).
3. Экспозиция: умножение на 2^EV.
4. Тональная кривая из контраста, светов, теней, белых и чёрных. Применяется к яркости с сохранением соотношения каналов, чтобы не плыл оттенок.
5. Линейный → sRGB.
6. Кривые: общая, затем R, G, B.
7. HSL и цветокоррекция по кругам в OKLCH.
8. Сочность и насыщенность: масштаб хромы в OKLCH; сочность слабее действует на уже насыщенные и телесные тона.
9. Импортированный LUT образа, если он задан.

Шаги 2–9 выполняются дважды: сначала с параметрами поправки фото, затем с параметрами образа. Кадр и поворот применяются поверх и в LUT не входят. Эталон — функция `core/color/pipeline.ts: (rgb, params) → rgb`; шейдер собирается из тех же параметров, а тест сравнивает оба результата на наборе изображений.

**Рендер.** Один контекст WebGL2 рисует всю сетку в общий canvas по координатам плиток. Кривые и HSL передаются в шейдер таблицами — строками float-атласа, которые шейдер читает и интерполирует сам, как эталон на CPU; импортированный LUT — 3D-текстурой. Крупный редактор одного фото работает в отдельном контексте на прокси 2048 px.

**Экспорт.** JPEG каждого поста в размере ленты (1080 × 1350 для 4:5, 1080 × 1440 для 3:4, 1080 × 1080 для 1:1), PNG всей сетки и порядок публикации снизу вверх с номерами. Пост режется из оригинала по кадру ленты, плитка сетки — по окну сетки, цвет — тот же конвейер, что на плитке. Файлы называются «1 — <имя фото>.jpg»: номер 1 у последней плитки сетки, её публикуют первой; опубликованные позиции пропускаются. `Сетка.png` — плитки 540 px с промежутками 4 px. Экспорт пишет в новую подпапку и ничего не перезаписывает (docs/decisions/0017-post-export.md).

## Модуль 2. LUT

Каждый образ экспортируется в 3D LUT, а по желанию и каждая связка «поправка фото + образ». В редакторе такой LUT даёт тот же результат, что превью Gridtone, но только если он применён в правильной точке обработки.

**Форматы.**

- `.cube` (формат Adobe и Resolve) размером 33 или 65. Вход и выход — sRGB с гаммой, домен 0..1.
- HaldCLUT PNG уровня 8 (512 × 512 px, куб 64³) — для darktable, RawTherapee и G'MIC.
- Импорт `.cube` в обратную сторону: чужой LUT становится образом проекта. Принимается только 3D `.cube` размером 2…65; 1D и shaper отвергаются, HaldCLUT не импортируется.

**Запекание.** LUT строится семплированием эталонной функции `pipeline` в узлах решётки N³; для N = 33 это 35 937 вызовов, доли секунды. Шейдер для этого не нужен: CPU-версия точнее и уже покрыта тестами.

**Проверка по кругу.** Тест прогоняет эталонные изображения через конвейер и через запечённый LUT с тетраэдрической интерполяцией, затем сравнивает. Порог: средний ΔE2000 < 0.5, 99-й перцентиль < 2. Если кривые с резкими изломами не проходят порог на размере 33, экспорт предлагает 65. Трилинейная интерполяция (так LUT по умолчанию применяет Resolve) считается и показывается отдельной строкой, на выбор размера не влияет.

**Где применять LUT.** Главное условие: изображение на входе LUT должно совпадать с тем JPEG, который вы загрузили в Gridtone. Отсюда рабочий цикл: экспортируете из редактора базовую версию (после проявки, до стилизации), строите на ней образ в Gridtone и возвращаете LUT в ту же точку обработки.

| Редактор | Формат | Куда ставить |
| --- | --- | --- |
| darktable | `.cube` или HaldCLUT PNG, модуль lut 3D | После проявки (filmic или sigmoid); пространство применения модуля — sRGB; папка с LUT указывается в настройках |
| DaVinci Resolve | `.cube` | Отдельный узел после перевода в Rec.709/sRGB |
| Photoshop | `.cube` | Корректирующий слой Color Lookup поверх базовой версии |
| Lightroom, Camera Raw | `.cube`, упакованный в профиль | Lightroom не читает `.cube` напрямую: профиль создаётся в Camera Raw через Photoshop (Create Profile с Color Lookup) и затем появляется в Lightroom |

**Калибровочная карта.** Gridtone экспортирует синтетическую таблицу цветов и градиентов. Вы применяете к ней LUT в своём редакторе, экспортируете и загружаете обратно. Приложение считает ΔE и подтверждает, что LUT стоит в правильной точке и редактор не меняет цвет по дороге. Карта возвращается файлом целиком — её можно уменьшить, но не обрезать и не повернуть: патчи находятся по пропорциям, без поиска на снимке. Замер сверяется с образом (вместе с его импортированным LUT), а не со связкой «поправка фото + образ».

**Пределы.** LUT не переносит кадр, виньетку, резкость, локальный контраст и маски. Кроме того, он одинаково обрабатывает все фото, поэтому кадры с разной экспозицией после него разойдутся. Выравнивать экспозицию и баланс белого нужно в редакторе до LUT, либо экспортировать отдельный LUT на каждый пост.

**Образ из референса.** Перенос стиля с чужой сетки (модуль 5) тоже строится как поточечное преобразование и поэтому запекается в LUT. Яркость переносится сопоставлением гистограмм L со сглаживанием в монотонную кривую. Цвет переносится сдвигом средних a и b и масштабом хромы к значениям референса. Ползунок силы смешивает результат с исходником.

## Модуль 3. Анализ и гармония

Анализ отвечает на три вопроса: держит ли сетка ритм по яркости, укладывается ли цвет в гармоничную схему и какие плитки выбиваются. Все метрики считаются по видимому окну 3:4 после правок, в воркере, на прокси 256 px. Обновляются они при каждом изменении.

**Метрики плитки.**

| Метрика | Как считается | Что даёт |
| --- | --- | --- |
| Яркость | Среднее и медиана OKLab L, перцентили 5 и 95 | Светлая или тёмная плитка, тональный диапазон |
| Ключ | Доли пикселей с L > 0.8 и с L < 0.3 | Высокий или низкий ключ |
| Температура | Среднее b (сине-жёлтая ось) с поправкой на a | Тёплая или холодная плитка |
| Насыщенность | Средняя хрома C, доля нейтральных пикселей (C < 0.03) | Яркие и приглушённые кадры |
| Доминанты | k-means на 5 кластеров в OKLab, вес пикселя растёт с хромой | Палитра плитки |
| Плотность | Энергия краёв по Собелю | Спокойный кадр или «шумный» |

Пороги L и C здесь — стартовые значения; их стоит откалибровать на реальных сетках на этапе 4.

**Метрики сетки.**

- Карта яркости 3 × N и разброс L между плитками.
- Контраст соседей: средняя разница L по горизонтали и по вертикали.
- Распознанный ритм: корреляция карты яркости с шаблонами (шахматка, полосы по строкам, по колонкам, диагональ, градиент). Показывается лучший шаблон и сила совпадения.
- Палитра сетки: доминанты всех плиток, сведённые k-means в 5–7 цветов с долями.
- Цветовое колесо: каждая плитка — точка с углом своего среднего тона и радиусом хромы.

**Гармония.** Используются тоновые шаблоны Мацуды (i, V, L, I, T, Y, X), как в работе Cohen-Or и соавторов «Color Harmonization» (SIGGRAPH 2006). Шаблон — набор секторов на цветовом круге: i — один узкий тон, V — аналоговая схема, I и X — пары противоположных тонов, T — половина круга (только тёплые или только холодные), L и Y — основной тон с акцентом. Алгоритм поворачивает каждый шаблон и ищет угол, при котором сумма выходов тонов за пределы секторов, взвешенная хромой, минимальна. Лучший шаблон — тип гармонии сетки, остаток — её оценка. Плитки с низкой хромой почти не весят, поэтому нейтральные сетки не получают ложных штрафов.

**Выбросы и исправления.** Плитка считается выбросом, если её L, температура или хрома отклоняются от цели (паттерна или соседей) больше допуска, либо её тон лежит вне секторов шаблона. Для каждого выброса приложение предлагает конкретную поправку:

- экспозиция — бинарный поиск EV по прокси до попадания в целевое L;
- температура — по сдвигу b;
- насыщенность — по отношению хромы плитки и цели;
- тон — сдвиг в HSL к ближайшему краю сектора.

Кнопка «Применить» записывает поправку в настройки фото. Ограничения силы (по умолчанию ±1 EV и ±20 по температуре) защищают кадр от разрушения: если цель за пределами лимита, плитка помечается «заменить».

**В интерфейсе** это панель «Анализ» в инспекторе: колесо тонов с наложенным шаблоном, полоса палитры, мини-карта яркости и список выбросов с кнопками исправления.

## Модуль 4. Паттерны

Паттерн задаёт цель для каждой позиции сетки: яркость, при необходимости тон и хрому, и допуск. Он повторяется вниз с периодом в несколько строк, поэтому план продолжается на любую глубину ленты.

**Откуда берётся паттерн.**

- **Генератор:** шахматка, полосы по строкам, полосы по колонкам, диагональ, градиент во времени (новые посты светлее или теплее), чередование двух цветов. Параметры: число уровней яркости, контраст, цвета.
- **Строка-шаблон** для быстрого ввода: строки по три символа, где `L`, `M`, `D` — светлый, средний и тёмный, например `LDL/DLD`.
- **Изображение с квадратами.** Сетка ищется автоматически: по профилям проекций (суммам градиентов по строкам и столбцам) находятся промежутки между ячейками. Поверх изображения всегда есть ручная сетка 3 × N, которую можно подвинуть, если автопоиск ошибся. Из каждой ячейки берутся центральные 60%: среднее в OKLab становится целью, а разброс показывает, плоская это заливка (жёсткая цель) или фото (мягкая цель).

**Устойчивость к сдвигу.** Каждый новый пост сдвигает всю сетку на одну позицию, и паттерн может развалиться. Шахматка на трёх колонках переживает сдвиг: меняет фазу, но остаётся шахматкой. Полосы по строкам держатся, только если публиковать пачками по три. Приложение помечает паттерн как «одиночные посты» или «пачками по 3» и строит план в порядке публикации. Закреплённые посты (до трёх) стоят первыми и в сдвиге не участвуют, это отдельная настройка сетки.

**Режим «Подогнать текущую сетку».**

1. Для каждой позиции с фото считается стоимость попадания в цель (формула — в модуле 5).
2. Авторасстановка: имеющиеся фото переставляются по позициям так, чтобы суммарная стоимость была минимальной. Это задача о назначениях, она решается венгерским алгоритмом. Опубликованные и зафиксированные позиции не двигаются.
3. На оставшиеся отклонения предлагаются поправки, как в модуле 3.
4. Плитки, которые нельзя довести до цели в пределах допустимых правок, помечаются «заменить» и уходят в подбор из библиотеки.

**Режим «План контента».** Пустые позиции получают карточки: номер в порядке публикации, образец целевой яркости и цвета, словесная подсказка («светлый, холодный, мало насыщенный») и подходящие кандидаты из библиотеки. Подсказка собирается автоматически из корзин L, температуры и хромы. План экспортируется в Markdown или CSV и картинкой целевой сетки.

## Модуль 5. Референс и подбор из библиотеки

Подбор ставит в каждую позицию фото из вашей библиотеки, ближайшее к цели по яркости и цвету, и даёт перебирать кандидатов прямо в сетке. Цели берутся из паттерна или из разобранной чужой сетки.

**Разбор чужой сетки.** На вход подаётся скриншот профиля с телефона или компьютера. Приложение отрезает интерфейс и ищет область из трёх колонок с тонкими однородными промежутками; поверх, как у паттернов, есть ручная сетка. Каждая плитка уже является окном 3:4, поэтому её признаки считаются так же, как у фото из библиотеки. На выходе — цели по позициям, общий образ (модуль 2) и палитра.

Скриншоты сжаты и сняты в разных темах интерфейса, поэтому допуски по умолчанию здесь шире, чем у паттерна из генератора. Скриншот используется только для анализа внутри проекта: приложение не скачивает чужие профили.

**Индекс библиотеки.**

- Источники — папки на диске. За изменениями следит chokidar, новые и изменённые файлы индексируются инкрементально.
- Для каждого файла сохраняются быстрый хэш (размер, дата изменения, xxhash первых и последних 64 КБ), EXIF, миниатюра 512 px, признаки по всему кадру и по центральному окну 3:4, dHash для поиска почти-дублей.
- RAW пока представлен встроенным JPEG-превью, которое достаёт exiftool-vendored.
- Хранение — SQLite: признаки, нужные для фильтров, лежат в колонках, полный вектор — в JSON.
- Позже, отдельным этапом, — смысловой поиск через CLIP (onnxruntime-node). Тогда к цели по цвету добавятся запросы вроде «море», «портрет», «детали».

**Стоимость кандидата.** Расстояние фото p до цели позиции s складывается из взвешенных частей:

```latex
\mathrm{cost}(p,s) = w_L \frac{|L_p - L_s|}{\tau_L} + w_h \frac{C_p}{C_{\max}} \cdot \frac{\Delta h(p,s)}{\tau_h} + w_C \frac{|C_p - C_s|}{\tau_C} + w_{pal}\, D_{pal}(p,s) + \Pi(p,s)
```

Здесь τ — допуски позиции, Δh — угловое расстояние тонов. Вклад тона умножается на хрому фото, потому что тон почти серого кадра не важен. D\_pal — расстояние палитр: доминанты жадно сопоставляются по ΔE в OKLab с весом по долям. Π — штрафы: фото уже стоит в сетке, почти-дубль соседа по dHash, кадр из той же серии в соседней позиции. Веса w регулируются ползунком «важнее яркость ↔ важнее цвет».

В режиме «с учётом коррекции» стоимость считается после лучшей допустимой поправки (экспозиция и температура в пределах лимитов). Так в выдачу попадают кадры, которые легко довести до цели.

**Поиск.** Сначала SQLite отбирает фото по диапазону L и корзинам тона, затем точная стоимость считается в памяти. Для набора пустых позиций лучший комплект без повторов находит венгерский алгоритм; для каждой позиции дополнительно хранятся топ-12 кандидатов.

**Перебор в позиции.**

- У выбранной позиции под сеткой открывается лента кандидатов с процентом совпадения и разбивкой «яркость / цвет / палитра».
- Стрелки ← → или колесо с Alt над плиткой меняют кандидата прямо в сетке; анализ и гармония пересчитываются сразу.
- Кадр нового кандидата ставится автоматически: окно 3:4 выбирается стратегией attention из sharp (самый заметный участок) и потом правится вручную.
- «Зафиксировать» закрепляет выбор. «Перераспределить» пересобирает остальные позиции с учётом зафиксированных.
- К кандидату одним действием применяется образ или поправка до цели.

## Этапы реализации

MVP — этапы 0–3: редактор с коррекцией и экспортом LUT полезен сам по себе и проверяет главную гипотезу «вижу в Gridtone — получаю в редакторе». Анализ, паттерны и подбор надстраиваются поверх, не трогая ядро. Каждый этап закрывается проверяемым критерием; без него следующий не начинается.

## Риски и открытые вопросы

Главный практический риск — LUT, применённый не в той точке обработки: тогда превью и результат расходятся, и весь проект теряет смысл. Остальные риски технические, и для каждого известно решение.

| Риск | Что делаем |
| --- | --- |
| LUT стоит не в той точке обработки | Рецепты по редакторам, калибровочная карта, проверка ΔE на этапе 3 |
| В готовых сборках sharp нет декодера HEIC (HEVC) | heic-decode (libheif в WASM) как запасной путь, на macOS — системный `sips` |
| Исходники iPhone в Display P3, устройства показывают цвет по-разному | Рабочее пространство sRGB, конвертация по встроенному ICC при импорте |
| Скриншоты референсов сжаты, сняты в светлой или тёмной теме, в разном масштабе | Широкие допуски, ручная сетка, предупреждение о качестве скриншота |
| 8 ГБ памяти на M1 | В памяти только прокси, LRU для текстур, индексатор пачками |
| Instagram снова меняет сетку | Пропорции и число колонок — параметры проекта, а не константы |
| Нативные модули (sharp, better-sqlite3) в сборке Electron | electron-rebuild, `asarUnpack`, отдельная CI-сборка под каждую платформу |

Открытые вопросы, которые стоит решить до начала:

- Какой редактор основной? От этого зависит, чей рецепт LUT делать первым и на чём проверять этап 3.
- Нужен ли RAW в первой версии или хватит экспортированных JPEG и TIFF?
- Нужно ли с самого начала несколько образов на сетку (например, два для шахматки) или хватит одного?
- Нужен ли смысловой подбор (CLIP), или цвета и яркости достаточно?

## Реализация в Claude Code

Один этап — одна сессия (большие этапы — две-три), а контекст между сессиями живёт в двух файлах: `docs/spec.md` и `docs/progress.md`. Чистое ядро `src/core` позволяет агенту работать в цикле «тест → код» без запуска Electron.

**Структура репозитория.**

```
gridtone/
├─ CLAUDE.md                 правила для агента
├─ docs/
│  ├─ spec.md                этот документ, экспортированный в Markdown
│  ├─ progress.md            журнал этапов: сделано, решения, что дальше
│  └─ decisions/             короткие ADR по спорным решениям
├─ shared/ipc.ts             единый контракт IPC
├─ src/
│  ├─ core/                  чистый TS: color, metrics, harmony, pattern, match, lut
│  ├─ main/                  Electron main: ipc, project, library (SQLite)
│  ├─ indexer/               utility process: sharp, признаки, миниатюры
│  ├─ preload/               типизированный мост
│  └─ renderer/              React UI, gl/ (шейдеры), workers/
└─ tests/
   ├─ core/                  Vitest
   ├─ golden/                эталонные изображения и ожидаемые значения
   └─ e2e/                   Playwright + Electron
```

**CLAUDE.md** — стартовая версия:

```markdown
# Gridtone

Десктоп-приложение для стилизации Instagram-сетки.
Спецификация: docs/spec.md. Статус и решения: docs/progress.md.

## Стек
Electron + electron-vite, TypeScript strict, React, Zustand + Immer, WebGL2,
sharp, better-sqlite3, Vitest, Playwright. Пакеты — npm.

## Команды
- npm run dev — запуск
- npm test — Vitest
- npm run test:e2e — Playwright
- npm run build — сборка

## Правила
- Логика цвета, метрик, гармонии, подбора и LUT — только в src/core, без DOM и Node.
- Конвейер цвета меняется синхронно в core/color/pipeline.ts и в шейдере;
  тест сравнения шейдера с эталоном обязан проходить.
- Новый алгоритм в core начинается с теста на синтетических данных.
- Все каналы IPC объявлены в shared/ipc.ts; renderer не трогает fs напрямую.
- Оригиналы фото никогда не перезаписываются.
- Новая зависимость — только с записью в docs/decisions/.
- В конце этапа обновить docs/progress.md: что сделано, решения, что дальше.
```

**Порядок работы.**

1. Экспортируйте этот документ в Markdown и положите в `docs/spec.md`.
2. Каждую сессию начинайте в режиме плана: агент читает нужный раздел спецификации и `progress.md`, предлагает план, вы его правите, потом идёт реализация.
3. Для `core` просите сначала тесты по разделу спецификации, затем код до зелёного.
4. Этап закрывается проверкой его критерия, коммитом и записью в `progress.md`. Следующая сессия стартует с чистым контекстом и восстанавливает его из этих двух файлов.
5. После крупного этапа запускайте ревью отдельным субагентом со свежим контекстом и задачей найти расхождения кода со спецификацией.

**Первый промпт** (этап 0):

