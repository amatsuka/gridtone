# 0015. Импорт LUT и шаг 9 конвейера

**Статус:** принято, 2026-10-08. Уточняет ADR 0010 и 0011.

**Контекст.** Спека: «Импорт `.cube` в обратную сторону: чужой LUT становится образом проекта», и шаг 9 конвейера — «импортированный LUT образа, если он задан». В модели данных у образа есть `importedLut?: string`, но не сказано, что в нём лежит и где сам файл. До этапа 3б `importedLut` менял только main (ADR 0010), а renderer не мог его ни задать, ни снять. Открытыми были вопросы:
- где хранится таблица в 1–8 МБ и как проект остаётся переносимым;
- кто и как назначает LUT образу, как это отменяется;
- что значит шаг 9 в числах: домен, интерполяция, выход за 0..1;
- что делать, если файл пропал.

**Решение.**

1. **Файл копируется в папку проекта** — `luts/<id>.cube`, байт в байт. id — первые 16 hex SHA-256 содержимого, как у ассетов (ADR 0003, 0004). Исходный файл не нужен после импорта, папка проекта переносится целиком.
2. **Реестр `Project.luts: Record<string, LutRef>`**, ключ — id:
   ```ts
   interface LutRef {
     id: string;         // первые 16 hex hash
     name: string;       // имя исходного файла, например «сепия.cube»
     size: number;       // LUT_3D_SIZE, 2…65
     hash: string;       // SHA-256 файла, hex
     importedAt: string; // ISO 8601
   }
   ```
   - `Look.importedLut` — id из реестра. Висячий id в project.json — повреждённый проект, как висячий `lookId`. Проект без `luts` открывается с пустым реестром.
   - **Реестр меняет только main** и только дописывает: запись не удаляется, когда LUT сняли или образ удалили. На ней держатся отмена «Снять LUT» и удаления образа. Уборка неиспользуемых записей и файлов — позже.
3. **Импорт** (`lut:import`, «Импорт LUT…» во вкладке «Образ» и «Файл → Импортировать LUT…»):
   - main спрашивает файл, читает его (до 32 МБ) и разбирает `parseCube` из core: только 3D 2…65, ошибки с номером строки (ADR 0014);
   - ошибка возвращается в renderer и показывается во вкладке «Образ», проект не меняется;
   - файл копируется с флагом `wx`: копия с тем же хэшем не трогается, а повреждённая заменяется атомарно — это копия проекта, а не файл пользователя;
   - запись реестра добавляется, если её нет. Повторный импорт того же файла реестр не дублирует, а пропавшую копию восстанавливает;
   - **новый образ — в конец `looks`**: нейтральная коррекция, `importedLut` — id, имя — TITLE из файла или имя файла без расширения. Импорт в историю не входит, как импорт фото.
4. **Main добавляет образы только в конец `looks`**, как слоты (ADR 0011): патчи истории адресуют образы по индексу. Правило записано в CLAUDE.md.
5. **Renderer назначает и снимает LUT** обычной правкой через `editProject`, поэтому «Снять LUT» и удаление образа с LUT отменяются. Инвариант ADR 0010 «`importedLut` не меняется» заменён: `importedLut`, если есть, — id из реестра `luts`. Корень `luts` в патчах по-прежнему запрещён. `duplicateLook` копирует ссылку на LUT.
6. **Шаг 9** — последний в проходе образа, после сочности и насыщенности (`applyBaked`, шейдер):
   - тетраэдрическая интерполяция `sampleLut` (ADR 0014): тот же выбор тетраэдра и те же веса в core и в шейдере;
   - вход вне домена `DOMAIN_MIN…DOMAIN_MAX` срезается к краю, выход срезается в 0..1, как на шагах 5 и 8;
   - у поправки фото LUT нет: за проход образа LUT один;
   - `PipelineParams.lut` — LUT образа; запекание, проверка по кругу, метрики и экспорт берут его через `applyBaked` сами. LUT образа в экспорте — коррекция образа и его импортированный LUT вместе.
7. **Шейдер.** Узлы — 3D-текстура RGB32F (R по x, G по y, B по z) без фильтрации, шейдер читает восемь узлов ячейки `texelFetch` и интерполирует сам, как таблицы этапа 1. Домен — uniform-векторы, бит `LUT3D` в флагах прохода. Константы по-прежнему из core.
8. **Загрузка.**
   - Renderer просит `lut:data` по id; main читает копию, сверяет хэш, разбирает и держит до 8 разобранных LUT. Разбор 65³ — около 110 мс (Node, эта машина), один раз за сессию на LUT.
   - В `PipelineGpu` — кэш 3D-текстур по id, до 8. Плитка, чей LUT ещё не загружен, не рисуется, как плитка без прокси.
   - Воркеры метрик и проверки по кругу получают LUT один раз по id. Ключи их кэшей включают id LUT: id выводится из содержимого, поэтому id определяет данные.
9. **Пропавший файл.** При открытии проекта main проверяет копии; статус — в снимке (`ProjectSnapshot.luts`), как статус ассетов. Если копии нет или хэш не совпал:
   - образ показывает предупреждение, шаг 9 в превью и метриках пропускается;
   - экспорт такого образа отказывается с сообщением: LUT без шага 9 обманул бы;
   - повторный импорт того же файла восстанавливает копию.

**Отвергнуто.**
- **LUT внутри project.json.** 1–8 МБ в каждом автосохранении и в снимках renderer.
- **Абсолютный путь к исходному `.cube`.** Проект перестал бы быть переносимым, а файл мог бы измениться после импорта.
- **Аппаратная трилинейная фильтрация 3D-текстуры.** Не совпала бы с тетраэдрической моделью core, а RGB32F без расширения не фильтруется.
- **Запрет renderer трогать `importedLut`.** Удаление образа с LUT не отменялось бы: обратный патч вернул бы образ с LUT, а main отверг бы его.
- **Удаление записи реестра вместе с последним образом.** Отмена удаления вернула бы образ со ссылкой в никуда.
- **Разбор `.cube` в utility process.** Лишний тип задачи ради 110 мс один раз на LUT; если на слабой машине это помешает, задача добавляется в `IndexerClient`, как экспорт LUT.

**Последствия.**
- Проект переносится папкой вместе с `luts/`; оригиналы фото по-прежнему по абсолютным путям.
- Реестр растёт с каждым импортом и не убирается сам.
- Новое изменение `looks` из main — только дописыванием в конец.

**Как проверяется.**
- Модульные тесты:
  - `tests/core/lut/step9.test.ts` — шаг 9 в `applyBaked`: последний в проходе образа, домен, срез выхода, запекание и проверка по кругу с LUT;
  - `tests/core/project.test.ts`, `tests/core/patch.test.ts`, `tests/core/looks.test.ts`, `tests/core/lutRegistry.test.ts` — реестр в `parseProject`, инварианты, копия образа, импорт в проект;
  - `tests/main/service.test.ts` — импорт через `ProjectService` до диска.
- `tests/e2e/shader-parity.spec.ts` — шаг 9 в шейдере против core на синтетических LUT.
- `tests/e2e/stage3b.spec.ts` — импорт, плитки, редактор, режим 5, экспорт, отмена, перенос папки, битые файлы.
