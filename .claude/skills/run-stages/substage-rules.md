# Общие правила для агента подэтапа Gridtone

Ты работаешь автономно в репозитории /Users/macbook/work/gridtone (Electron-приложение Gridtone). Пользователь ушёл и оставил компьютер включённым: задавать вопросы некому, AskUserQuestion не используй. Спорные решения принимай сам. Бери разумный дефолт, согласованный со спекой и прежними ADR. Решения записывай в docs/progress.md, а заметные — в новый ADR в docs/decisions/ под следующим свободным номером.

Это та же работа, которую пользователь делал бы в новой сессии командой «выполни подэтап X по плану».

## С чего начать
1. Прочитай CLAUDE.md, его правила обязательны. Затем docs/progress.md: план текущего этапа целиком (общие пункты, нужный подэтап, «Отличия от спеки») и записи последних выполненных подэтапов. Особенно их «Дальше»: там заметки для следующего.
2. Прочитай нужные разделы docs/spec.md и относящиеся к делу ADR в docs/decisions/.
3. Посмотри, как сделаны последние подэтапы (git log, git show --stat), и следуй тем же приёмам и стилю кода.

## Как работать
- Выполни подэтап по плану целиком: критерий, указанный e2e, модульные тесты, ADR из шагов плана. Новый алгоритм в core начинается с теста на синтетических данных.
- Новых зависимостей не добавляй, если план их не предусматривает и без них можно обойтись. Если всё же нужна — ADR по правилам CLAUDE.md.
- **React StrictMode в `npm run dev` монтирует эффекты дважды.** Если эффект отпускает ресурс (контекст WebGL, воркер, подписку), при повторном монтировании он должен создавать ресурс заново, а не брать прежний. Пример: холст редактора фото, коммит 1b1b94a. e2e собирают продакшн и такие поломки не видят.
- **e2e при заблокированном экране macOS может зависать** («Находки» этапа 2а).
  - Запускай `npm run test:e2e` в фоне или с разумным таймаутом и следи за выводом.
  - Если тест завис из-за окружения, перезапусти его отдельно: `npx playwright test <файл>`. Не жди бесконечно.
  - Если окружение так и не дало прогнать e2e, честно запиши это в журнал и в отчёт.
- Перед коммитом должны проходить `npm run typecheck`, `npm test` и `npm run test:e2e`. e2e — все, включая прежние этапы и shader-parity.
- Убедись, что новый e2e не пустой: если сломать проверяемое поведение (мутация), тест должен падать. Результат укажи в журнале.
- То, что требует глаз пользователя или настоящих сторонних редакторов, подэтап не блокирует. Вынеси это в ручной чек-лист или в «Отложено».

## Закрытие подэтапа
- Допиши в конец docs/progress.md раздел «## Этап <id>. <Название> — <сегодняшняя дата>» в том же формате и стиле, что прежние записи: Критерий, Как проверяется, Что сделано, Решения, Находки, Отличия от спеки, Дальше. Если это последний подэтап этапа:
  - в «Дальше» напиши, что этап закрыт и следующий шаг — план следующего этапа;
  - в «Отложено» собери всё отложенное с этапа.

  Пиши кратко, по-русски, в стиле существующих записей.
- Если появилось правило, которое должны соблюдать следующие сессии (единственное место расчёта, запрет, инвариант), добавь его строкой в CLAUDE.md.
- Сделай один коммит в main. Ветку не создавай, push не делай. Сообщение в стиле предыдущих: заголовок «Этап <id>: <кратко>», пустая строка, маркированный список, затем строка
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
- После коммита `git status` должен быть чистым: временные файлы — в .gitignore или удалены.
- Если что-то из плана сделать не удаётся, доведи остальное до рабочего состояния, в котором проходят тесты. Недоделанное опиши в журнале («Отличия от спеки» / «Дальше») и всё равно закоммить.

## Финальный ответ оркестратору
Не длиннее 200 слов:
- хэш коммита;
- выполнен ли критерий;
- результаты typecheck, npm test (число тестов) и e2e;
- ключевые решения;
- что отложено или сломано;
- что важно знать следующему подэтапу.
