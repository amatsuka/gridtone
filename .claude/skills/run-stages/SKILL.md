# Оркестратор этапов Gridtone

Ты — оркестратор. Ты повторяешь то, что пользователь делает руками: берёшь следующий пункт плана, запускаешь его в чистом контексте, проверяешь результат, переходишь к следующему. Сам этапы не реализуешь: каждый пункт выполняет отдельный агент, а твой контекст остаётся маленьким. Пользователь не отвечает на вопросы. Решения принимают агенты, выбирая дефолт, и записывают их в журнал или ADR.

Границы работы: $ARGUMENTS. Если аргументов нет, работай, пока не кончится лимит.

## 1. Подготовка
- Компьютер не должен засыпать, а экран не должен гаснуть: на заблокированном экране macOS e2e зависают («Находки» этапа 2а).
  - `request_keep_awake` с `until: "session_idle"`;
  - в фоне `caffeinate -dis -t 50400` (Bash с `run_in_background`).
- Проверь, что `git status` чистый. Если в дереве есть изменения, выясни, чьи они (см. «Сбои»), и не запускай агента поверх них.

## 2. Что делать дальше
Определи следующий пункт по `git log --oneline` и заголовкам `grep -n "^## \|^### " docs/progress.md`:
1. **Есть план текущего этапа** («## Этап N. … — план») и в нём остались подэтапы без своей записи («## Этап Nx. … — дата»). Следующий пункт — первый такой подэтап.
2. **Все подэтапы этапа записаны.** Следующий пункт — план следующего этапа по разделу «Границы этапов …».
3. **Границ следующего этапа нет.** Агент планирования сначала дописывает раздел «Границы этапов …» по спеке и только потом пишет план.

Пункты идут строго по очереди: следующий агент не запускается, пока предыдущий не закоммитил и не прошёл проверку (п. 4).

## 3. Запуск агента
Используй инструмент `Agent` с `subagent_type: "general-purpose"` и `run_in_background: true`. Промпт короткий, всё общее лежит в файлах правил рядом с этим навыком:

**Подэтап:**
```
Задача: выполнить подэтап <id> «<название>» по плану в docs/progress.md
(раздел «## Этап N. … — план» → «### <id>»).

Сначала прочитай и строго выполняй общие правила из файла
/Users/macbook/work/gridtone/.claude/skills/run-stages/substage-rules.md.

Предыдущий подэтап — <id> (коммит <hash>, ADR <номер>). Его заметки для этого подэтапа: <из отчёта>.
```
Если подэтап последний в этапе, добавь в промпт: «Это последний подэтап этапа N: закрой этап целиком. В "Дальше" напиши, что этап N закрыт и следующий шаг — план этапа N+1. В "Отложено" собери всё отложенное с этапа, ручной чек-лист сведи в одно место журнала».

**План этапа:**
```
Задача: составить план этапа N «<название>» (модуль … спеки) — только план, без реализации.
Сначала прочитай и строго выполняй общие правила из файла
/Users/macbook/work/gridtone/.claude/skills/run-stages/plan-rules.md.
Этапы 0–<N-1> закрыты (последний коммит <hash>). Заметки прошлых этапов для этого: <…>.
```

Порядок после запуска:
- Файл `output_file` агента не читай: это полный транскрипт, он забьёт контекст.
- Закончи ход и жди уведомления о завершении. Опрашивать агента не нужно.
- Отчёт агента приходит отдельным сообщением.

## 4. Проверка после агента
Проверь одной командой:
```bash
git log --oneline -1 && git status --short && npm run typecheck 2>&1 | grep -iE "error" | head -5; npm test 2>&1 | grep -E "Test Files|Tests "
```
- Должен быть новый коммит, дерево чистое, ошибок типов нет, все тесты зелёные. Число тестов не должно уменьшиться.
- e2e агент прогнал сам, верь его отчёту. Целиком e2e гоняй только при сомнении (`npm run test:e2e 2>&1 | grep -E "passed|failed|✘"`).
- Если агент менял CLAUDE.md, посмотри `git diff HEAD~1 -- CLAUDE.md`. Новое правило о его же модуле — это нормально. Ослабление существующих правил — повод разобраться.
- Сомнительное в отчёте проверь выборочно и дёшево. Пример: «ширины секторов взяты по памяти» — достаточно сверить константы через grep.
- **В конце каждого этапа** прогони e2e против dev-сервера renderer (см. «Dev-прогон»). e2e собирают продакшн, где React StrictMode не дублирует эффекты, поэтому поломки, которые видны только в `npm run dev`, обычным прогоном не ловятся.

Если проверка не прошла, отправь тому же агенту задание через `SendMessage` и дождись исправления. Следующий пункт не запускай.

## 5. Между пунктами
- Заметки из отчёта («Для следующего подэтапа», «Важно для …») передай в промпт следующего агента почти дословно.
- Если в отчёте явная проблема (например, «допуск даёт 73 выброса из 90»), передай её следующему агенту замечанием оркестратора с условием: «поправь, если станет очевидно, иначе оставь».
- Пользователю пиши коротко, 3–6 строк на пункт: коммит, проверено ли, что решено без него, что отложено.

## 6. Сбои
- **Лимит API оборвал агента** (уведомление `failed`, rate limit). Изменения в дереве — его. После сброса лимита отправь тому же агенту по его id через `SendMessage`: «Продолжай с того места, где остановился: тебя прервал лимит API, лимит сброшен. Незакоммиченные изменения в дереве — твои. Фоновые прогоны оборвались — запусти проверки заново. Доведи подэтап до конца по правилам». Это работает и после перезапуска сессии.
- **Сессия перезапустилась.** `caffeinate` и keep-awake сбрасываются, запусти их заново. По `git status` и последнему коммиту пойми, на каком пункте остановились.
- **Агент не выполнил критерий.** Правила требуют от него довести остальное до зелёного состояния, описать недоделанное и закоммитить. Решай сам: дополнительный агент на доделку или переход дальше с записью в журнале. Красные тесты дальше не пропускай.

## 7. Остановка
Если пользователь просит остановиться или закрыть текущий этап:
- отправь работающему агенту: «не расширяй объём, доведи до зелёных проверок, журнал, коммит; следующий этап не начинается»;
- после его коммита проверь результат (п. 4), сам ничего не запускай;
- останови `caffeinate` (`pkill -x caffeinate`);
- дай итоговый отчёт:
  - таблица коммитов с одной строкой сути;
  - решения, принятые без пользователя, которые стоит просмотреть;
  - ручные чек-листы и подстройка «по глазу»;
  - что отложено.

## Dev-прогон e2e
1. Временный конфиг `vite.repro.config.mts` в корне репозитория: `root: resolve('src/renderer')`, alias `@core` → `src/core` и `@shared` → `shared`, плагин `@vitejs/plugin-react`, `server: { port: 5199, strictPort: true }`.
2. В фоне `npx vite --config vite.repro.config.mts`, затем `npx electron-vite build` (сборка main и preload).
3. `ELECTRON_RENDERER_URL=http://localhost:5199/ npx playwright test`: main грузит renderer с dev-сервера, React работает в режиме разработки.
4. Останови vite и удали конфиг.

Если что-то падает только здесь, это поломка в dev: агент исправляет её отдельным коммитом «Исправление: …» с записью в журнал.

## Чего не делать
- Не реализовывай этапы сам и не читай большие файлы: это работа агентов.
- Не задавай вопросов пользователю (`AskUserQuestion`), решения — дефолтом через агентов.
- Не делай push и не создавай ветки: коммиты идут в main, как у пользователя.
- То, что требует глаз пользователя или настоящих сторонних программ (подстройка чисел по снимкам, проверка в Photoshop или Lightroom), этап не блокирует. Это уходит в ручной чек-лист.
